OSINT MAPPER - ANALYST EXPERIENCE AND FAULT REVIEW
Date: 4 October 2026 (Asia/Calcutta)
Reviewer: Codex, critically reviewing the current implementation

PURPOSE
Review this tool as an analyst trying to collect information, distinguish facts
from guesses, investigate relationships, and produce a defensible dossier.
This document contains findings and fixing ideas. It does not implement fixes.

OVERALL VERDICT
The app is a useful working prototype. I would not yet trust it as my only
investigation record. The most serious problems are losing edits, silently
overwriting newer work, and confusing recorded names with verified identities.
The interface looks more finished than the underlying workflow currently is.
My earlier description of the app as polished was too strong.

An analyst should be able to answer five questions immediately:
1. What do I know about this subject?
2. Where did each statement come from?
3. How certain is it, and what contradicts it?
4. What should I investigate next?
5. Is my latest work safely saved?
The current app only answers these consistently for uncomplicated examples.

HOW THIS REVIEW WAS DONE
- Read the current backend, templates, forms, graph, export, and storage code.
- Used the fictional sample, not real people or private investigation data.
- Reproduced interaction failures with the actual frontend scripts in a DOM
  test environment, including delayed saves and keyboard interaction.
- Tested backend behavior through an isolated HTTP server and temporary SQLite
  database. Existing saved dossiers were not edited or deleted by these probes.
- Examined a generated 501-node graph to check the actual SVG fit calculations.
- Read current template definitions from the running local app.

Important limit: no live browser or desktop surface was available in this
session. DOM tests verify behavior, not real browser rendering, eye comfort,
screen-reader output, or touch ergonomics. Those visual concerns are marked
as requiring a browser check. This is an analyst simulation and technical
review, not a completed usability study with human participants. It is not
a claim that every possible fault has been discovered.

EVIDENCE LABELS
REPRODUCED: observed in an isolated interaction or HTTP test.
CODE-CONFIRMED: directly established by implementation or configuration.
USABILITY JUDGMENT: likely analyst friction; validate with real users.

PRIORITIES
P0: fix before using the app as the primary record of important research.
P1: next work needed for dependable analyst use.
P2: usability, delivery, and operational improvements.

FAST READING: THE FIRST FIVE FIXES
1. Protect drafts and stop stale saves from replacing newer work.
2. Give people, companies, accounts, projects, and sources stable IDs.
3. Link evidence to specific claims and relationships through source IDs.
4. Make the default map show useful relationships, with record clutter optional.
5. Replace the long mandatory-looking worksheet with a short capture workflow.


A. SAVING AND TRUST
===================

01. Work typed during a save can disappear
Priority: P0 | Evidence: REPRODUCED
Fault: The save captures the form, waits for the server, then redraws it using
that earlier snapshot. Inputs remain editable while waiting. Later edits are
replaced, and the interface can say "All changes saved."
Reproduction: Enter "First saved edit" in Current role, save with a delayed
response, then type "Later edit while saving." The first value returns.
The same failure was reproduced with analyst notes.
Analyst impact: I lose research while believing it was safely saved.
Fix: Keep a separate draft with an edit revision. Acknowledge only the revision
sent to the server; retain newer edits and show that they are still unsaved.
Add recoverable local drafts and visible Saving / Saved / Save failed states.
Pass condition: Editing while a request is pending never removes newer text.

02. Two tabs can silently overwrite each other's changes
Priority: P0 | Evidence: REPRODUCED THROUGH HTTP
Fault: Every save replaces the entire dossier without checking its revision.
Reproduction: Two copies of one dossier are loaded. A saves important notes.
B saves a new finding using the old copy. The notes revert to the old value.
Analyst impact: I cannot safely compare sources in multiple tabs or recover
which version was correct.
Fix: Add a dossier revision and reject stale writes with a conflict response.
Show the conflicting fields and offer an explicit merge. Preserve revisions.
Pass condition: A stale save cannot silently replace a newer dossier.

03. Opening and canceling another action can disable draft protection
Priority: P1 | Evidence: REPRODUCED
Fault: allowNavigation clears dirty flags before an action actually completes.
The warning offers Discard, even when the destination is only a dialog.
Reproduction: Edit a worksheet, open Rename, accept the discard prompt, and
cancel Rename. The old edited form remains visible. Leaving it now produces
no further warning, and its displayed draft disappears.
Analyst impact: The draft shown on screen no longer matches the app's idea
of whether it needs protection. Similar confusion applies to canceled import
pickers or other actions that call the same navigation helper.
Fix: Clear dirty state only after an actual save or completed discard.
Prefer Save and continue / Keep editing / Discard, with a recoverable draft.
Pass condition: Canceling an action leaves draft protection consistent.

04. Finding dialogs do not protect unfinished entries
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: Dirty tracking covers worksheets and notes, but not the finding dialog.
Cancel or Escape can close an unfinished finding without retaining it.
Analyst impact: A long evidence explanation can vanish with one keypress.
Fix: Keep dialog drafts, ask before discarding a changed entry, and provide
Resume draft. Show save errors inside the active dialog rather than relying
only on a temporary notice behind its backdrop.
Pass condition: Accidental dialog closure does not permanently lose a draft.

05. Several write actions can be submitted repeatedly while pending
Priority: P1 | Evidence: REPRODUCED
Fault: The finding form permits multiple simultaneous writes. The test sent
two requests from a rapid repeated submit. Creating dossiers and saving notes
also lack a consistent pending-operation guard.
Analyst impact: Repeated clicks during a slow save can create duplicate
dossiers or race updates. Two finding writes do not necessarily create two
findings, but they are still independent competing saves.
Fix: Disable the submitting action while pending, show progress, and use
idempotency keys for create operations. Keep failures recoverable.
Pass condition: Repeated clicks result in one intended write.

06. There is no useful change history or undo for evidence edits
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: The database keeps the latest dossier document. Removing a saved
finding has no trash entry or Undo; replacing evidence leaves no revision log.
Analyst impact: I cannot explain who changed an assessment, restore an
accidentally deleted claim, or compare today's conclusion with yesterday's.
Fix: Record meaningful revisions with timestamps, changed fields, and optional
analyst attribution. Add Undo to removals and a readable history view.
Pass condition: A saved claim or finding can be restored after an accidental edit.


B. IDENTITY AND EVIDENCE ACCURACY
================================

07. Matching names are treated as matching identities
Priority: P0 | Evidence: REPRODUCED
Fault: Graph entities are merged by lowercased, trimmed display names.
Reproduction: Two intended entities named Mercury, one an employer and one
an academic collaborator, become one node. Conversely, an abbreviation or
alternate spelling can create a separate node for the same organization.
Analyst impact: The map can imply a connection to the wrong person or company.
Fix: Use stable entity IDs, explicit types, aliases, and distinguishing details.
Suggest possible matches, but let the analyst confirm a merge or separation.
Pass condition: Namesakes remain separate unless deliberately merged.

08. Entity types are incomplete and depend on how records are entered
Priority: P1 | Evidence: REPRODUCED
Fault: Connections have no From/To type selector. An entity first created as
generic is not upgraded when later fields provide a more specific type.
Observed: In the sample, Northstar Demo Labs is correctly an organization,
but Harbor Demo Foundation and Jordan Demo remain generic entities.
Project Lantern Demo also has no dedicated project type. A separate company
fixture left its explicitly described partner company typed as generic.
Analyst impact: Colors and type filters can mislead me or hide useful records.
Fix: Let analysts choose Person, Organization, Account, Domain, Project, or
another supported type. Store the type independently of form ordering.
Pass condition: A company's identity and filter behavior do not depend on
whether it was first entered through a profile or a connection.

09. Repeated links overlap and can look like stronger evidence
Priority: P1 | Evidence: REPRODUCED AND CODE-CONFIRMED
Fault: Profile, Connections, and People & partners can generate equivalent
links. Parallel links use the same straight-line geometry and label midpoint.
Observed: The sample has five links between the subject and Northstar Demo
Labs, including two works at links and three related affiliation labels.
Multiple supported by links are also repeated.
Analyst impact: I see clutter and may mistake repeated entry for independent
confirmation. Overlapping labels make individual links hard to distinguish.
Fix: Canonicalize relationship types, combine duplicate assertions, retain
their separate evidence records, and curve truly different parallel links.
Pass condition: One employment relationship can show several supporting
sources without pretending to be several independent relationships.

10. Source references are fragile text rather than maintained links
Priority: P1 | Evidence: REPRODUCED
Fault: S01 references are parsed from text using a limited token split.
Reproduction: [S01] produced no supported by link. The backend accepted two
different source records both labeled S01; the graph's reference lookup then
uses the last matching source. Renaming/removing a source has no reference check.
Analyst impact: Evidence can point nowhere or at the wrong document.
Fix: Select sources through a searchable source picker with stable IDs.
Enforce unique display references and warn about broken references on import
or deletion. Support migration of existing text references.
Pass condition: A claim retains its exact source even when its label changes.

11. Evidence links are not precise enough to support a specific assertion
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: For manual connections, supported by links are attached to the From
and To nodes, rather than to a durable relationship assertion. Some partner
fields also become relationship-looking edges without per-field provenance.
Analyst impact: A source about a person can appear to support all surrounding
connections, although it may establish only one particular employment fact.
Fix: Give each assertion an ID and attach sources, excerpts, dates, and
confidence to that assertion. Show exactly which claim the source supports.
Distinguish analyst grouping links from evidence-backed real relationships.
Pass condition: Selecting works at shows its own evidence, not just general
sources associated with either endpoint.

12. Strong certainty labels can be recorded without supporting evidence
Priority: P1 | Evidence: REPRODUCED THROUGH HTTP; PERMITTED BY THE FORMS
Fault: A verified finding or confirmed connection can be saved with no source
or evidence. The graph does not visually distinguish confidence consistently.
Analyst impact: A confident-looking map can be based entirely on assumptions.
Fix: Keep quick entry possible, but flag unsupported certainty and require
evidence or an explicit justification when promoting a claim. Display a
clear evidence status; use consistent styling for uncertain connections.
Pass condition: Unsupported claims cannot quietly look evidence-confirmed.

13. Confidence means different things in different parts of the app
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: Findings use Low/Medium/High and Verified/Unverified/Hypothesis.
Worksheet claims use Confirmed/Corroborated/Probable/Possible/Unverified/
Contradicted. There is no defined conversion or unified review filter.
Analyst impact: I do not know whether a high-confidence finding is equivalent
to a confirmed claim, or how to list every unresolved assertion.
Fix: Separate verification state from confidence and source quality, then
use the same definitions everywhere. Provide an Unresolved claims view.
Pass condition: The same assertion has consistent meaning in every view.

14. Numerical importance scores create precision without a clear rubric
Priority: P2 | Evidence: USABILITY JUDGMENT; CONFIGURATION CONFIRMED
Fault: Seven subjective scores are added into a /70 total. The help does not
define concrete scoring anchors or when these dimensions suit an inquiry.
Analyst impact: I spend time guessing numbers that look objective to readers.
Academic or market influence may be irrelevant to the actual investigation.
Fix: Make scoring optional and purpose-specific. Give practical anchors,
record reasoning and evidence, and label totals as analyst judgment.
Pass condition: Two analysts understand what the same score is intended to mean.

15. Import validation is weaker than the interface suggests
Priority: P1 | Evidence: REPRODUCED THROUGH HTTP
Fault: The API accepted invalid dates, invalid source URLs, duplicate source
references, and schemaVersion 999. Some type checks exist, but these values
and supported schema versions are not consistently validated.
Analyst impact: A file can import successfully yet behave differently when
edited; native date fields may not represent malformed imported date strings.
Fix: Validate dates, allowed URL schemes, uniqueness, known versions, and
required relationships. Preview import issues and migrations before saving.
Preserve unsupported data explicitly rather than silently normalizing it away.
Pass condition: Successful import means the data can be viewed and edited
without unexpected loss or reinterpretation.


C. DAY-TO-DAY RESEARCH WORKFLOW
==============================

16. The default worksheet is too large and too research-oriented
Priority: P1 | Evidence: CONFIGURATION CONFIRMED; USABILITY JUDGMENT
Fault: Each template contains 14 sections and 90 defined fields before any
repeat entries. Several sections still assume academic research, collaborators,
grants, or institutional influence, even for a general person/company inquiry.
Analyst impact: It feels like a form-completion exercise rather than a useful
place to collect a few facts. I may fill irrelevant fields just to feel finished.
Fix: Start with Basics, Facts, Connections, Sources, and Next steps. Let the
analyst enable optional research, ownership, or other investigation modules.
Pass condition: A simple dossier can be useful without opening most sections.

17. The same information belongs in too many places
Priority: P1 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: A fact can be entered in Findings, Claims & evidence, Key findings,
Summary, People & partners, Connections, or Notes. Several can repeat the same
value without sharing a maintained underlying record.
Analyst impact: I ask "where do I put this?" and later edit one copy while
forgetting the others. Duplicate graph links are one visible consequence.
Fix: Store one factual assertion and let summaries, evidence views, and maps
reference it. Keep raw notes clearly separate from curated conclusions.
Pass condition: Updating one employment fact updates its relevant views.

18. Help explains vocabulary better than it teaches a concrete next action
Priority: P2 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: Many field tips reuse broad section advice. A beginner can still wonder
what a good entry looks like, how much evidence is enough, or when to stop.
Small hover controls and long tips need real browser and touch testing.
Analyst impact: The extra instructions become reading work rather than guidance.
Fix: Add a short example, a specific public-source starting point where useful,
and a clear "leave blank if unknown" instruction. Offer a pinned help panel
for longer explanations and keep tooltip text short.
Pass condition: A new analyst can enter their first supported fact without
reading all the help or understanding specialized research terminology.

19. The analyst cannot adapt the worksheet to their investigation
Priority: P2 | Evidence: CODE-CONFIRMED
Fault: General finding labels are flexible, but worksheet sections and fields
are fixed. There is no module selection, custom section, or reusable custom
template for a different type of inquiry.
Analyst impact: I work around the framework instead of letting it help me.
Fix: Hide irrelevant modules, add optional custom fields, and support saved
template presets. Keep stable IDs and a migration plan for existing data.
Pass condition: A non-academic inquiry does not inherit unnecessary research sections.

20. Blank fields cannot explain what is actually unknown
Priority: P2 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: A blank can mean not researched, researched but not found, not applicable,
or deliberately excluded. These states are not represented.
Analyst impact: Another reader cannot tell whether a gap is an unfinished task
or the result of completed research.
Fix: Allow optional Not checked / Not found / Not applicable states and a
short explanation. Do not turn filling every field into a completion target.
Pass condition: The dossier distinguishes missing work from a documented negative result.

21. Capturing one useful web finding requires too much repeated typing
Priority: P1 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: An analyst manually copies URLs and information into separate sources,
claims, findings, relationships, and notes. There is no single capture action
that creates a reusable source and links it to a fact.
Analyst impact: I lose research momentum and forget provenance while switching forms.
Fix: Add Quick capture: paste a URL, add the fact and excerpt, choose or create
a subject, and save. Reuse the source throughout the dossier. Any later page
metadata collection should remain explicit and show errors honestly.
Pass condition: One captured fact and its source require one coherent action.

22. The timeline does not show the investigation's complete chronology
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: The timeline includes only additional findings and sorts collection
dates. It excludes worksheet claims, sources, connections, and actual event dates.
Observed: The sample has many dated sources and assertions, but only three
additional findings are eligible for the timeline.
Analyst impact: I can mistake the order of collection for the order of events.
Fix: Separate Event date, Publication date, and Collected date. Offer an event
timeline and a research activity history, with approximate dates clearly marked.
Pass condition: A source found today about an old appointment appears in the
correct event period rather than implying the appointment happened today.

23. Separate dossiers do not form a shared investigation
Priority: P1 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: The graph is built from one dossier at a time. A connection's target
is a text name, not a link to another saved person/company dossier. There are
no case folders, case objectives, or shared entities across the workspace.
Analyst impact: I cannot naturally follow an individual to the company dossier
I already created, and the same source or entity is repeatedly entered.
Fix: Add cases containing linked entity dossiers and shared sources. Let the
analyst open an existing entity from a connection and choose case-wide mapping.
Pass condition: A person and their company can share one maintained connection
and be investigated together without copying records between dossiers.


D. GRAPH NAVIGATION AND INTERPRETATION
=====================================

24. The map is readable as a diagram but weak as an editing workspace
Priority: P1 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: Selecting a node displays details, but does not provide Edit this fact,
Open its worksheet entry, or Open the cited source record. The analyst must
change tabs, find the section, and locate the right repeated entry manually.
Analyst impact: The map is a presentation layer rather than a practical place
to investigate and correct evidence.
Fix: Add stable record IDs and direct edit/jump actions in the details panel,
with safe draft handling. Make source references clickable within the app.
Pass condition: From a questionable map connection I can reach its exact
evidence record and edit it without searching the entire worksheet.

25. Search and filtering remove the context needed to understand a match
Priority: P1 | Evidence: REPRODUCED AND CODE-CONFIRMED
Fault: Graph search filters node labels/properties rather than graph relationship
labels. Nonmatching neighbors disappear, so matching nodes can look isolated.
Observed: Searching funds in the sample left two visible nodes and no visible
links, although a funds relationship existed. Sidebar search also matches raw
storage field names: Overall Importance Score returned a dossier by its schema.
Analyst impact: A technically matching result can feel unrelated or incomplete.
Fix: Search entities, assertions, and relationship labels separately. Highlight
matches while preserving useful neighbors. Offer Focus result and Clear search.
Search sidebar content through a display index, not raw serialized JSON.
Pass condition: Searching funds reveals the recorded funding connection and endpoints.

26. Dense graphs become tiny, and Fit view can still crop large maps
Priority: P1 | Evidence: REPRODUCED GEOMETRY; VISUAL COMFORT NEEDS BROWSER QA
Fault: All graph links share a fixed radial layout rather than a layout tuned
to the question being investigated. Full dossier records add many extra nodes.
Text shrinks with zoom, and fit clamps zoom to a minimum of 0.08.
Observed: A 501-node fixture had 254 node centers outside the SVG viewport
after Fit view. This is a computed geometry result, not a screenshot judgment.
Analyst impact: I have to zoom and hunt; a complete-looking overview can hide nodes.
Fix: Start with a neighborhood or relationship-only overview. Keep claim/source
expansion optional, allow grouping and edge filters, use suitable layouts,
and make fit truly include the selected scope. Provide a searchable table view.
Pass condition: Fit view includes every node in its stated scope, and useful
labels remain readable at realistic laptop sizes and graph sizes.

27. My graph arrangement disappears when I leave the tab
Priority: P2 | Evidence: REPRODUCED
Fault: Node positions, zoom, and other view state are recreated when the map
renders again. Manual arrangement was lost after switching tabs. Export also
builds a fresh view rather than preserving the analyst's arranged presentation.
Analyst impact: I repeatedly rebuild the same layout and cannot export the
specific visual story I just prepared.
Fix: Save positions and view presets per dossier. Separate data export from
Export this view, preserving layout, scope, and visible filters.
Pass condition: Returning to the map or exporting the view preserves the arrangement.

28. Keyboard focus is lost when a graph node is inspected
Priority: P2 | Evidence: REPRODUCED
Fault: Drawing replaces all SVG node elements. Pressing Enter on a focused
node selected it but moved focus to BODY in the DOM test.
Analyst impact: Keyboard exploration repeatedly loses its place. Large sets
of individually tabbable nodes and edges can also be tiring to navigate.
Fix: Update existing elements or restore focus by stable ID. Provide an
accessible node list, neighbor navigation, and clear keyboard shortcuts.
Pass condition: Keyboard selection preserves a predictable focus position.
Check actual browser accessibility output before claiming screen-reader support.

29. Headline counts do not measure what an analyst needs to know
Priority: P2 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: Sources combines registered source entries with source-bearing findings.
The sample shows seven under Sources despite having four registered source
entries; it is not a deduplicated source count. Saved records counts several
different kinds of entries rather than evidence-supported facts.
Analyst impact: High counts can feel like progress while claims remain unresolved.
Fix: Use clearly defined metrics: unique registered sources, sourced claims,
unresolved claims, missing evidence, and actionable next steps. Explain counts.
Pass condition: The number shown matches the list opened by clicking it.


E. OUTPUT, RECOVERY, AND OPERATIONS
==================================

30. Export includes all recorded details, even after narrowing the map
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: The HTML export serializes the full graph model, including analyst
notes. Search, filters, and collapsed branches do not remove that data from
the export. An export can therefore contain more than the analyst thinks they
are showing. This matters particularly when notes include unreviewed hypotheses.
Analyst impact: Sharing a filtered-looking report could disclose internal notes
or unsupported claims that were intended to stay within the working dossier.
Fix: Add an export preview, scope selection, internal/public presets, and
explicit inclusion controls for notes, leads, uncertainty, and sources.
Explain that hiding nodes on screen is not redaction. Redacted exports must
remove excluded values from the serialized payload, not just the display.
Pass condition: An excluded internal note is absent from the exported file itself.

31. There is no concise final assessment for a reader who dislikes graphs
Priority: P2 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: The final deliverables are a data JSON file or an interactive graph.
There is no guided readable report with the key questions, conclusions,
contradictions, evidence citations, and outstanding gaps in one narrative.
Analyst impact: I still have to manually write the actual investigation report
for a colleague or manager who needs answers rather than a map.
Fix: Add a human-readable dossier report assembled from reviewed assertions,
with source references, scope, collection dates, limitations, and next steps.
Keep the analyst in control of conclusions; generate structure, not invented facts.
Pass condition: A reader can understand the important findings without exploring every node.

32. Starting, stopping, and troubleshooting the app require technical effort
Priority: P2 | Evidence: CODE-CONFIRMED; USABILITY JUDGMENT
Fault: Running the app requires Python and a server process. The launcher does
not provide a normal start/open/status/stop experience. The green Local workspace
indicator is static rather than a live check of connection and saving ability.
Analyst impact: I worry whether the app is actually running, why it cannot save,
or whether closing the terminal will interrupt the investigation.
Fix: Provide a one-click local launcher, open the correct URL, show actual
server/connection state, and give actionable port, database, and save errors.
Keep the local deployment simple; do not add a large server stack just for appearance.
Pass condition: An analyst can launch and recover the app without reading server logs.

33. Backup and storage protection are outside the workflow
Priority: P1 | Evidence: CODE-CONFIRMED
Fault: There is no in-app full-workspace backup/restore or automatic backup.
The README recommends copying the SQLite file while the app is stopped.
Storage and exports are not encrypted, and there is no application login.
The server does bind to loopback; it is not currently exposed as a public service.
Analyst impact: A workstation failure or accidental database loss could remove
the investigation. Local storage alone does not make confidential data protected.
Fix: Add a tested backup/restore flow using SQLite's backup API, dated snapshots,
and clear file locations. Offer encrypted backups or workspace protection when
confidential use requires it. State the single-user local security model plainly.
Pass condition: A user can restore a backed-up case and verify its contents.

34. Delete means Trash, and there is no deliberate permanent removal flow
Priority: P2 | Evidence: CODE-CONFIRMED
Fault: DELETE marks a record deleted; it remains in the database. This is useful
for recovery, and the dialog explains it, but there is no Empty trash or
per-dossier permanent removal. Existing JSON/HTML exports also remain separate files.
Analyst impact: I cannot complete a deliberate retention cleanup from the app.
Fix: Keep recoverable deletion as default. Add an explicit permanent removal
action with confirmation, clear limits, and backup/export reminders. Explain
that removing a live dossier cannot remotely erase copies already exported.
Pass condition: Recovery and deliberate removal are clearly different actions.

35. Existing tests prove basic mechanics, not reliable analyst experience
Priority: P1 | Evidence: CODE-CONFIRMED AND THIS REVIEW
Fault: The committed suite tests backend templates, scores, migration, and
delete/restore. Prior DOM checks covered happy-path entry and graph controls.
They did not catch save races, stale writes, identity ambiguity, fragile source
references, focus loss, or large-map fit. Frontend checks are not part of a
reproducible committed test suite, and real browser visual QA remains outstanding.
Analyst impact: Passing checks gave more confidence than the product deserved.
Fix: Add regression tests for these reproduced faults and a small set of real
browser scenarios. Test realistic cases, not only whether a node count matches.
Include laptop-sized screens, long source text, 100-500 nodes, failed/delayed
saves, imports, restoration, keyboard use, and selective export.
Pass condition: A release cannot regress the analyst's work protection or
evidence interpretation while still passing its advertised checks.


WHAT SHOULD BE KEPT
===================
- Local-first operation and the small deployment footprint.
- SQLite persistence, plus portable JSON import/export.
- Recoverable dossier deletion and the clearly fictional sample.
- Plain labels and inline help, refined with examples rather than removed.
- Clickable graph details and a self-contained offline map option.
- Existing HTML escaping and HTTP/HTTPS link restrictions in graph output.
- Stable legacy field IDs while display labels become simpler.

WHAT A SIMPLER ANALYST PRODUCT SHOULD FEEL LIKE
==============================================
Default workspace: Overview | Facts | Connections | Sources | Next steps.
Map is another way to explore the same maintained records, not a second database.
Optional detailed research modules stay available without dominating the start.

Suggested normal workflow:
1. Create a case and identify the subject with a stable entity ID.
2. Capture a source and one factual assertion together.
3. Mark its evidence status; add a dated connection if the source establishes one.
4. Review unresolved questions and conflicting evidence.
5. Explore a focused map or a readable list; edit either without duplicating facts.
6. Produce a scoped report with clear citations and controlled inclusion of notes.

Keep auto-saving unobtrusive, but always show whether a draft is durable.
Keep unknowns visible, but do not reward filling irrelevant fields.
Keep the map attractive, but let evidence and identity decide what it means.

RECOMMENDED FIX ORDER
=====================
Stage 1 - Protect the investigation
Issues 01-06: draft handling, save revisions, safe navigation, write guards,
history, and undo. Also validate imports before relying on the stored data.

Stage 2 - Make the information trustworthy
Issues 07-15: explicit entity types/IDs, maintained source links, assertion-level
evidence, confidence consistency, duplicate handling, and import validation.
Migrate existing records carefully; never silently merge names during migration.

Stage 3 - Reduce the work needed to use it
Issues 16-23: smaller default workflow, one capture action, shared records,
optional modules, meaningful unknown states, real timelines, and case linking.

Stage 4 - Make the map support investigation
Issues 24-29: edit/jump actions, contextual search, useful map scope, true fit,
saved layouts, keyboard navigation, and meaningful counts.

Stage 5 - Make results portable and recoverable
Issues 30-34: export preview/redaction, readable reports, a normal launcher,
backup/restore, and deliberate retention controls.

Regression testing from issue 35 should accompany every stage, not wait until
the end. No reliable effort estimate is possible until the revised data model
and intended investigation workflow are chosen.

SMALL ACCEPTANCE EXERCISE BEFORE CALLING IT READY
================================================
Give a new analyst a short case with two namesakes, one company, two conflicting
sources, one expired affiliation, and one unresolved online account. Ask them
to capture facts, connect entities, correct a mistake, work in two tabs, return
after an interruption, and export a colleague-facing report.

The analyst should succeed without losing work, merging namesakes, confusing
collection time with event time, or exposing private working notes. They should
be able to explain each important link from its specific evidence. Measure
where they hesitate rather than only how many fields they complete.

TECHNICAL POINTERS FOR IMPLEMENTING THE FIXES
===========================================
app.py: validate, do_POST, do_GET; whole-document writes and schema validation.
static/app.js: save, renderContent, form submit handlers, raw JSON sidebar search.
static/template-ui.js: allowNavigation, renderTemplate, draft flags, full form redraw.
static/graph.js: buildGraph/entity, linkSources, layout, visibleNodes, draw,
                inspectNode, fit, and exportGraph.
static/product.js: rename/delete/trash transitions and pending-action handling.
templates.py: template scope, source fields, confidence choices, scoring/help.
test_app.py: extend coverage beyond the current backend happy paths.
